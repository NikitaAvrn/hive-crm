## 1. Проблема и цель

**Проблема.** Семья ведёт быт в разрозненных инструментах: задачи — в мессенджере, бюджет — в Excel, кредиты — в голове, напоминания — в календаре телефона. Нет единого места, где видно «кто, что, когда и за сколько».

**Цель.** Единая система для ведения семейных дел: пространства (личное, семья, друзья), задачи, заметки, чат, финансы с кредитным калькулятором, календарь и файлы — с низким порогом входа и работой на телефоне.

**Метрики успеха (пример):**
- ≥ 80% членов семьи заходят ≥ 3 раз в неделю через месяц после запуска.
- ≥ 90% регулярных платежей (квартплата, подписки) заводятся как запланированные расходы.
- Время на создание задачи с телефона ≤ 15 секунд.

## 2. Пользователи и роли

| Роль | Возможности |
|---|---|
| Владелец пространства | Полный доступ, приглашения, удаление пространства |
| Взрослый участник | CRUD задач/заметок/финансов в пространстве |
| Ребёнок / ограниченный | Чтение бюджета, свои задачи, без редактирования финансов |
| Гость (read-only) | Просмотр по ссылке (опционально, вне MVP) |

**Ключевое требование:** пространства изолированы; владельцы разных пространств не пересекаются. Один пользователь может состоять в нескольких пространствах с разными ролями.

Удаление — soft delete с TTL 30 суток; восстановление доступно владельцу; по истечении TTL — каскадное физическое удаление, кроме финансовых транзакций (архивируются) и аудита (хранится 1 год)

## 3. Границы MVP (MoSCoW)

| Приоритет | Что входит |
|---|---|
| **Must** | Пространства + роли, проекты/каталоги, задачи (статусы, сроки, приоритеты, назначение, подзадачи), заметки (Markdown), учёт доходов/расходов, **периодические операции (доходы и расходы)**, **прогноз баланса**, **отчёт «план vs факт»**, календарь (агрегированный + по пространствам), файлы (метаданные + вложения) |
| **Should** | Чат (polling/SSE), делегирование задач, напоминания о периодических операциях. «Комплектующие / ресурсы» (этап 2, после финансов): учёт расходных материалов для хобби-проектов (электроника, ремонт, рукоделие). Сущности: Item (название, категория, единица = штуки, место хранения, текущий остаток qty), StockMove (приход/расход/списание, delta, дата, автор, опционально projectId и unitCost, комментарий). Остаток по проекту — вычисляемый (сумма движений с projectId). Связи с финансами нет. Полноценный складской учёт (партии, сроки годности, инвентаризация, UoM-конвертация)  |
| **Could** | Кредитный калькулятор с изменением ставки, расширенные отчёты/статистика, уведомления (email/push), PWA offline |
| **Won't (v1)** | Импорт банковских выписок, мобильные нативные приложения, гость read-only |

> Кредитный калькулятор — самый ценный и самый дорогой модуль. Рекомендуется вынести его в отдельный этап после стабилизации ядра.

## 4. Функциональные требования (по модулям)

### 4.1 Пространства

- Динамическое создание; типы: личное, семейное, друзья, кастомное.
- Изоляция данных; приглашение по ссылке-инвайту.
- Один пользователь — N пространств, роль в каждом своя.

### 4.2 Каталоги (проекты)

- Вложенность (дерево), привязка к пространству.
- Задачи и заметки могут принадлежать каталогу или быть «в корне».

### 4.3 Задачи

- Поля: заголовок, описание (Markdown), статус (todo/in progress/done/blocked), срок, приоритет (low/normal/high/urgent), назначенный, автор, родительская задача, теги.
- Подзадачи — через `parentId`; прогресс родителя считается автоматически.
- Делегирование = смена `assignee` с записью в аудит.

### 4.4 Заметки

- Markdown (GFM), drag-and-drop изображений, привязка к пространству/каталогу/задаче.

### 4.5 Чат

- Каналы = пространства; сообщения с привязкой к задаче (комментарии).
- Транспорт: polling или SSE (WebSocket — вне MVP, обосновать в ТЗ).

### 4.6 Финансы

«Курсы валют загружаются с API ЦБ РФ ежедневно, кэшируются в ^RATES(date, currency). При недоступности API — используется последний кэш; при отсутствии кэша — операция в небазовой валюте блокируется с ошибкой».

#### 4.6.1 Счета и транзакции

- Счета: наличные, карта, накопительный, вклад. Поля: название, тип, валюта, текущий остаток.
- Транзакции: доход/расход, сумма, валюта, дата, категория, счёт, комментарий, автор.
- Категории: иерархические, свои для каждого пространства.
- поле rateToBase в транзакции (снимок курса).

#### 4.6.2 Периодические операции (запланированные доходы и расходы)

Единая сущность `Recurring` с полями:

| Поле | Описание |
|---|---|
| `direction` | `income` / `expense` |
| `amount` | Сумма |
| `currency` | Валюта |
| `category` | Категория |
| `account` | Счёт |
| `schedule` | Ежемесячно / ежеквартально / ежегодно / кастомный (cron-подобный) |
| `nextDate` | Дата следующей операции |
| `endDate` | Опционально, дата окончания |
| `remindBefore` | За сколько дней напоминать |
| `autoCreate` | Создавать транзакцию автоматически или только напоминать |
| `loanId` | Опционально, ссылка на кредит (для платежей по кредиту) |

**Примеры доходов:** зарплата, аванс, пенсия, детские пособия, аренда, проценты по вкладу, фриланс (нерегулярный — `autoCreate: false`, с ручным подтверждением).

**Примеры расходов:** квартплата, подписки, ипотека, кружки детей, страховка.

**Правила:**
- Платёж по кредиту — это `Recurring` с `direction: expense` и ссылкой на `Loan`. Кредитный калькулятор генерирует/обновляет периодическую операцию.
- Нерегулярные доходы (фриланс, подработки, продажа вещей) — `Recurring` с `autoCreate: false` (система напоминает, пользователь подтверждает сумму) либо тип «ожидаемый разовый доход».
- Пропущенные платежи при `autoCreate: true` — создаётся «черновик» транзакции, подсвечивается в UI для подтверждения пользователем.
- Валюта: хранится `amount` + `currency`; конвертация — по курсу на дату. Для MVP допускается одна валюта, поле заложено на будущее.

Для месячных операций: если указанный день отсутствует в месяце — используется последний день месяца (31 → 28/29/30). В UI показывается подсказка.

#### 4.6.3 Прогноз баланса

- На основе `Recurring` + текущих остатков строится кривая ожидаемого остатка на N дней вперёд.
- Подсветка периодов отрицательного баланса («кассовый разрыв»).
- Прогноз — вычисляемый слой; «фантомные» записи в основной журнал не создаются.

#### 4.6.4 Отчёты

- **«План vs факт»** по доходам и расходам за период: запланировано / фактически / отклонение.
- По категориям, по периодам, сводка по пространству.

### 4.7 Кредитный калькулятор (этап 2)

- Сущность `Loan`: тело, ставка, срок, дата начала, тип платежа (аннуитет/дифференцированный).
- Возможность изменить ставку с даты X (рефинансирование) и пересчитать график.
- Выход: график платежей с разбивкой «тело / проценты», итоговая переплата, остаток долга на дату.
- Связь: автоматическое создание/обновление `Recurring` (расход) по дате платежа.

### 4.8 События и календарь

- Базовая сущность «Событие»; задача — частный случай события (со статусом), встреча — без статуса.
- Представления: агрегированный календарь по всем пространствам (с цветовой маркировкой) + фильтр по пространству.
- Напоминания: за N минут/дней (email/push в Should).

### 4.9 Файлы

- Метаданные в MUMPS, бинарники — в ФС/S3.
- Привязка к пространству/задаче/заметке.
- Лимит размера, список допустимых типов.

### 4.10 Учёт ресурсов (этап 2)

- `Item`: название, категория, `unit` (шт/л/м — простой enum, без конвертации), место (текст), `qty` (денормализованный), `minQty` (опц.).
- `StockMove`: `itemId`, `delta` (+/−), `date`, `author`, `unitCost` (опц., приход), `comment`, `contextId` (опц.).
- `Context`: `type` (`project` / `vehicle` / `property` / `other`), `name`. Простой справочник; атрибуты (марка, VIN, пробег) — **не в v1** (это модуль «Активы»).
- Остаток по контексту — вычисляемый: сумма `delta` по движениям с данным `contextId`.
- При `qty <= minQty` — подсветка + опц. задача «купить X».
- Связи с `Transaction` нет (осознанно, v1).
- Идемпотентность: движение создаётся атомарно с обновлением `qty` (TSTART/TCOMMIT).
- Отчёты: «что есть», «что ушло на <контекст>», «пора купить», «где лежит X».

### 4.11 Долги (этап 2)

- `Debt`: `direction` (`lent` — мне должны / `borrowed` — я должен), `counterparty` (текст), `amount`, `currency`, `account`, `date`, `dueDate` (опц.), `status` (`open` / `partially_repaid` / `closed` / `written_off`), `comment`, `remindBefore` (опц.).
- Выдача долга: `Transaction` типа `transfer` со счёта на виртуальный счёт `Account.type = receivable` («Дебиторка: <контрагент>»). Баланс реального счёта уменьшается; общий баланс не меняется (актив переехал).
- Возврат: обратный `transfer`; `Debt.status` обновляется (`partially_repaid` / `closed`). Частичные возвраты — несколько `transfer`, привязанных к `Debt`.
- Напоминание: отдельный джоб по `dueDate - remindBefore`; `Recurring` не используется (чтобы не размывать его семантику).
- Прощение долга (`written_off`): `Transaction` типа `expense` (категория «прощённые долги») с виртуального счёта — тогда это реальный расход.
- Отчёт: «кто мне должен», «кому я должен», «просроченные».

## 5. Архитектура (концептуально)
Vue 3 + Pico CSS (SPA/PWA)
│ REST/JSON (тонкий слой)
▼
Web API на MUMPS (маршрутизация, JSON-сериализация)
│
▼
Глобалы MUMPS (иерархия пространств)
│
├── ФС/S3 — бинарные файлы
└── Очередь уведомлений (email/push)

**Принципы:**

- Фронтенд не знает о древовидной структуре глобалов — только плоский JSON.
- Бинарные данные не хранятся в глобалах.
- Транзакционность финансовых операций — на стороне MUMPS (TSTART/TCOMMIT).
- Аудит изменений финансов и задач — в отдельном глобале.

**Эскиз глобалов (для ТЗ):**
^SPACE(id) ; метаданные
^SPACE(id,"members",user) ; роли
^SPACE(id,"projects",projId)
^SPACE(id,"tasks",taskId)
^SPACE(id,"notes",noteId)
^SPACE(id,"finance","accounts",accId)
^SPACE(id,"finance","txn",txnId)
^SPACE(id,"finance","recurring",recId) ; периодические операции
^SPACE(id,"finance","loans",loanId)
^SPACE(id,"events",eventId)
^SPACE(id,"files",fileId)
^SPACE(id,"audit",timestamp)
<!-- ^SPACE(id,"inventory","items",itemId)
^SPACE(id,"inventory","items",itemId,"moves",moveId) -->
^SPACE(id,"inventory","items",itemId)
^SPACE(id,"inventory","moves",moveId)
^SPACE(id,"inventory","contexts",ctxId) ; type, name
^SPACE(id,"inventory","items",itemId,"moves",moveId) ; индекс по товару
^SPACE(id,"inventory","contexts",ctxId,"moves",moveId) ; индекс по контексту
^SPACE(id,"finance","debts",debtId)
^SPACE(id,"finance","accounts",accId) ; type: cash/card/savings/receivable/payable

Выбор СУБД — MUMPS. Обоснование: (1) разряженная природа данных (пространства с разным набором сущностей) — MUMPS хранит только то, что есть, без NULL-колонок и миграций схемы; (2) масштабирование модели данных без DDL — добавление полей и уровней иерархии не требует миграций; (3) стоимость инфраструктуры — MUMPS закрывает нагрузку на порядки дешевле SQL-стоек при данном профиле (много мелких операций, глубокая иерархия); (4) экспертиза команды — ключевой фактор. Ограничения приняты осознанно: узкий рынок разработчиков (bus factor), отсутствие готовых ORM/observability — компенсируется экспертизой и дисциплиной разработки.

## 6. Нефункциональные требования

- **Производительность:** отклик API ≤ 300 мс на типовых операциях; календарь за месяц ≤ 1 с; прогноз баланса на 90 дней ≤ 500 мс.
- **Мобильность:** адаптив под 360 px; PWA (offline-заглушка в Could).
- **Безопасность:** аутентификация (сессии/JWT), проверка роли на каждом эндпоинте, изоляция пространств на уровне запросов к глобалам.
- **Резервное копирование:** ежедневный дамп глобалов.
- **Локализация:** ru (старт), архитектурно — готовность к en.

## Как оформить физически

- **Формат:** Markdown в репозитории (`docs/concept.md`) + экспорт в PDF для согласования. Версионирование через git, ревью в PR.
- **Шаблон:** структура IEEE 29148 (SRS) или Lean Canvas для раздела «проблема/цель». Для внутреннего проекта достаточно разделов выше.
- **Правило:** каждый раздел — со статусом (draft / agreed / TBD), чтобы на встрече обсуждать не «что написано», а «что ещё не решено».
