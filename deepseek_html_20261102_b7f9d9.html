Назначение и принципы

Документ описывает модель данных HomeBase для MUMPS и API-слой поверх неё. Цель — дать разработчику единый источник истины по сущностям, полям, связям и физической схеме глобалов.

Принципы

  • Пространство — корень изоляции. Все сущности принадлежат пространству через spaceId. Кросс-пространственных запросов нет, кроме агрегированного календаря (§4.8) — и то через явный список spaceId пользователя.
  • Плоский JSON на API, дерево — в глобалах. Фронтенд не знает о структуре глобалов. API отдаёт и принимает плоские объекты, бэкенд раскладывает по дереву.
  • Деньги — в копейках. Все суммы хранятся как целые числа в минимальной единице валюты (копейки, центы). Валюта — отдельное поле, для MVP одна на пространство.
  • Время — в UTC. Даты и время хранятся в UTC ISO 8601. Отображение — в часовом поясе пространства (поле timezone).
  • Транзакционность финансов. Изменение баланса счёта и запись транзакции — в одной транзакции MUMPS (TSTART/TCOMMIT). Иначе баланс разъедется.
  • Аудит — отдельно. Изменения финансов, задач и настроек пишутся в ^SPACE(id,"audit"), чтобы не смешивать с основными данными.
  • Мягкое удаление. Пользовательские сущности (задачи, заметки, транзакции) не удаляются физически, а помечаются deletedAt. Жёсткое удаление — только для пространства целиком, по явному запросу.

Соглашения по именованию

  • Глобалы — заглавными: ^SPACE, ^USER, ^SPACE_BY_USER.
  • Поля внутри узлов — строчными: "name", "createdAt", "assigneeId".
  • ID — строки (UUID v4 или монотонный счётчик с префиксом). Для MUMPS удобнее строки, чтобы не зависеть от счётчика.
  • Даты — ISO 8601 в UTC: "2025-03-28T10:00:00Z".

ER-диаграмма

Связи между сущностями. Ромб — сущность, линия — связь с кардинальностью (1:N, N:M). Диаграмма рендерится Mermaid, если подключён CDN; иначе — текстовая схема ниже.

Mermaid загружается с CDN. Если диаграмма пустая — откройте документ при доступе в интернет или используйте текстовую схему ниже.

Схема глобалов MUMPS

Физическая структура. Каждый глобал — дерево с ключами-строками. Данные пространства — под ^SPACE(spaceId). Пользователи — отдельный глобал ^USER, чтобы авторизация не зависела от пространства.

Верхний уровень

^USER(userId) # профиль: name, email, passwordHash, createdAt ^USER(userId,"sessions",sessionId) # активные сессии (если сессии, не JWT) ^USER_BY_EMAIL(email,userId) # индекс для логина ^SPACE_BY_USER(userId,spaceId) # обратный индекс: в каких пространствах состоит ^INVITE(token) # приглашения, чтобы принимать без знания spaceId ^SPACE(spaceId) # корень пространства "meta" # name, kind, ownerId, currency, timezone, createdAt "members"(userId) # role, joinedAt, invitedBy "projects"(projectId) # name, parentId, color "tasks"(taskId) # title, status, assigneeId, dueDate… "notes"(noteId) # title, body, taskId… "events"(eventId) # type, start, end, recurrence… "channels"(channelId) # kind, name, members "msgs"(msgId) # authorId, body, taskId, attachments "files"(fileId) # name, size, mime, storageKey "finance" # финансы пространства "accounts"(accId) # name, kind, balance, currency "categories"(catId) # name, parentId, direction "txn"(txnId) # direction, amount, accountId… "recurring"(recId) # direction, amount, schedule, nextDate "loans"(loanId) # principal, rate, termMonths… "rate_changes"(changeId) # newRate, effectiveDate "early_payments"(payId) # amount, date, mode "budgets"(budgetId) # categoryId, period, amount "audit"(ts,counter) # actorId, entity, action, diff

Индексы для частых запросов

# Задачи по назначенному (быстрый фильтр «Мои») ^SPACE(spaceId,"idx","tasks_by_assignee",userId,taskId) = "" # Задачи по сроку (для календаря месяца) ^SPACE(spaceId,"idx","tasks_by_due",date,taskId) = "" # Транзакции по счёту и дате (для отчётов) ^SPACE(spaceId,"idx","txn_by_account",accId,date,txnId) = "" # Транзакции по категории и периоду (для «План vs факт») ^SPACE(spaceId,"idx","txn_by_cat",catId,date,txnId) = "" # Recurring по nextDate (для прогноза и напоминаний) ^SPACE(spaceId,"idx","recurring_by_next",nextDate,recId) = "" # События по дате (для календаря) ^SPACE(spaceId,"idx","events_by_start",date,eventId) = "" # Сообщения канала в обратном порядке (последние сверху) ^SPACE(spaceId,"channels",chId,"idx","msgs_by_time",-ts,msgId) = ""

Как хранятся деньги

Только целые копейки. Никаких float. В MUMPS числа хранятся как строки, но арифметика — в целых. amount = 684000 для 6 840 ₽. Валюта — отдельно, в currency. Это единственный способ не разъехаться на аннуитете за 111 платежей (см. открытый вопрос №4 в концепте).

Транзакционность

; MUMPS: создание транзакции + обновление баланса — атомарно TSTART ; 1. пишем транзакцию SET ^SPACE(sp,"finance","txn",txnId,"amount") = 234000 SET ^SPACE(sp,"finance","txn",txnId,"accountId") = accId SET ^SPACE(sp,"finance","txn",txnId,"direction") = "expense" ; 2. обновляем баланс счёта SET ^SPACE(sp,"finance","accounts",accId,"balance") = ^SPACE(sp,"finance","accounts",accId,"balance") - 234000 ; 3. пишем аудит SET ^SPACE(sp,"audit",$ZDT($H,3),counter,"entity") = "txn" SET ^SPACE(sp,"audit",$ZDT($H,3),counter,"actorId") = userId TCOMMIT

Ключи и ID

  • ID — строки с префиксом: sp_ (space), u_ (user), t_ (task), n_ (note), acc_ (account), txn_ (transaction), rec_ (recurring), loan_ (loan). Это упрощает чтение логов и не зависит от счётчика.
  • Генерация — UUID v4, обрезанный до 12 символов, либо отдельный счётчик ^COUNTER("task"). Для MVP — UUID, чтобы не блокировать на счётчике.
  • Даты — строки "2025-03-28", время — "2025-03-28T10:00:00Z". Строковое сравнение работает как временно́е, если формат фиксирован (ISO 8601).
  • Сортировка по времени — через SET ... "idx","by_time",-ts,id, где ts — unix timestamp. Обратный порядок — отрицательное число.

Ошибки

{ "error": { "code": "FORBIDDEN", "message": "Роль child не может редактировать финансы", "field": null } }
Проверка роли на каждом эндпоинте. Если в URL есть :id пространства — первым делом проверяется, что пользователь в нём состоит и его роль допускает действие. Это не middleware «после», а первая проверка в обработчике, иначе получится IDOR.

Правила целостности

Что должно быть гарантировано на уровне бэкенда, а не UI. Каждое правило — либо транзакция MUMPS, либо проверка в обработчике.

Обязательные проверки

  • Пространство. Все сущности в запросе принадлежат одному spaceId. Кросс-пространственные связи запрещены (кроме агрегированного календаря по явному списку).
  • Роль. Действие разрешено ролью. child не может редактировать финансы, adult не может удалить пространство, только owner может менять владельца.
  • Деньги. amount — целое > 0. balance пересчитывается в той же транзакции, что и txn.
  • Переводы. direction=transfer требует toAccountId, и он ≠ accountId. Оба счёта существуют и в одном пространстве.
  • Recurring → Loan. Если loanId задан, direction должен быть expense, а accountId совпадать с loan.accountId.
  • Категории. categoryId существует и его direction совпадает с txn.direction. Для перевода категория не обязательна.
  • События. end ≥ start. Для recurrence — until ≥ start.
  • Сообщения. Если taskId задан — задача существует в том же пространстве.
  • Файлы. Размер ≤ лимита пространства, MIME в белом списке.
  • Soft-delete. Удалённые сущности не возвращаются в API по умолчанию. Явный запрос ?includeDeleted=true — только для владельца и только для аудита.

Что делать при удалении

  • Задача. Soft-delete. Подзадачи остаются, но при запросе родителя отдаются как «сироты». Файлы и заметки, привязанные к задаче, остаются.
  • Заметка. Soft-delete. Файлы остаются, ссылки в задачах — нет (заметка не упоминается в задаче, только задача в заметке).
  • Транзакция. Soft-delete + пересчёт баланса счёта (обратная операция). Перевод — две обратные операции.
  • Счёт. Архивация (isArchived: true). Удаление запрещено, если есть транзакции. Архивный счёт не показывается в фильтрах, но его транзакции доступны.
  • Категория. Архивация. Транзакции с этой категорией остаются. Новые — нельзя.
  • Кредит. Soft-delete. Связанный Recurring — либо архивируется, либо отвязывается (пользователь выбирает).
  • Участник. Удаление из members. Сущности, где он был автором/назначенным, остаются. Назначенный → null.
  • Пространство. Soft-delete на 30 дней, потом hard-delete. До истечения — восстановление владельцем.

Открытые вопросы

То, что в концепте (§7) помечено как риски, и что нужно решить до старта разработки бэкенда. Каждый вопрос — с вариантами и рекомендацией.

№ Вопрос Варианты Рекомендация
1 Аутентификация на MUMPS Сессии (глобал ^USER(id,"sessions",sid)) vs JWT Сессии проще: logout = удалить узел, нет проблем с отзывом JWT. JWT удобнее для мобильного, но в MVP мобильного нативного нет — PWA работает с сессией.
2 Реальное время чата Polling vs SSE vs WebSocket Polling раз в 3–5 секунд. SSE — если понадобится «печатает…». WebSocket — вне MVP, обосновать в ТЗ.
3 Хранилище файлов ФС vs S3 ФС на старте (проще, дешевле), S3 — когда перерастёт один сервер. Абстракция storageKey уже есть.
4 Точность округлений в кредитах Копейки (int) vs рубли (int) vs decimal Только копейки (int). Округление — «половина вверх» на каждом шаге. Для 111 платежей иначе накопится расхождение в сотни рублей.
5 Импорт банковских выписок CSV vs API банка CSV — в Should, API — вне MVP. Ключевая сложность — маппинг категорий, заложить в Budget и Category поле aliases.
6 Уведомления: email vs push Email (SMTP) vs Push (PWA) Email на старте — проще, работает везде. Push — в Should, через Service Worker.
7 Мультивалютность Одна валюта в MVP vs сразу несколько Одна на пространство. Поле currency есть в модели, конвертация — вне MVP.
8 Пропущенные Recurring Черновик транзакции vs автозапись vs пропуск Черновик с draft: true и подсветкой в UI. Пользователь подтверждает или отклоняет. Это компромисс между «не потерять» и «не записать лишнего».
9 Кредитные карты Отдельный тип Loan vs счёт с отрицательным балансом Счёт с отрицательным балансом. У кредитной карты нет фиксированного срока и аннуитета — это не кредит, а revolving-линия. Не смешивать.
10 Часовой пояс UTC на бэкенде + TZ пространства vs локальное время UTC в хранении, TZ пространства в отображении и в генерации Recurring. Иначе «выпить таблетку в 20:00» сдвинется при поездке.
